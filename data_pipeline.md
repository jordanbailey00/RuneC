# RuneC Data Pipeline Plan

This document owns the data-pipeline design for RuneC_v4. It complements:

- `data_cleanup.md`, which owns the migration sequence.
- `git_setup.md`, which owns Git and release-data distribution.

The pipeline goal is stricter than the current repo state:

- RuneC must not require cloned reference repos inside the RuneC tree.
- Runtime must run from RuneC code plus RuneC runtime packs.
- Exporters must not read `data/source/runelite`, `data/source/osrsreboxed-db`,
  `data/source/data_osrs`, `tools/cache_pipeline/source/rsmod`, VoidPS,
  2011Scape, Near-Reality, Zenyte, or any other mirrored repo.
- If another repo has logic or facts RuneC needs, convert the needed behavior
  into RuneC-owned code, tables, schemas, and tests before the pipeline uses it.
- External repos may be read off-repo as research references, but they must not
  be build, runtime, exporter, or setup dependencies.

## Dependency Policy

Use this distinction everywhere:

- **Reference:** something a developer reads outside the RuneC repo to
  understand OSRS behavior.
- **Dependency:** something RuneC code, setup scripts, tests, exporters, or
  runtime data generation reads automatically.

References are allowed only as research material. Dependencies on external
RuneScape repos are not allowed in the steady state.

The only normal user data acquisition path should be:

```bash
./scripts/setup-data.sh
```

That command should read `runtime-data.lock`, download RuneC-published runtime
data when the lock points to an official release, verify checksums, and install
it locally. While the lock is draft/non-official, it must refuse default remote
downloads and require either `--offline dist-data` or explicit release URL
overrides. It should not clone or read RuneLite, RSMod, osrsreboxed, data_osrs,
VoidPS, 2011Scape, Near-Reality, Zenyte, or RuneC-DB.

Maintainer rebuilds may use raw b237 cache input, but that input should live
outside the RuneC repo root and be passed explicitly. The pipeline should never
expect a hidden checkout under `data/source/` or `tools/cache_pipeline/source/`.

## Native Replacement Rule

When a needed fact currently comes from another repo:

1. Identify the exact fact or behavior RuneC needs.
2. Determine whether b237 cache data can produce it.
3. If the cache cannot express it directly, create a small RuneC-owned
   curated table under `content/` with source notes.
4. If logic is needed, implement it in RuneC code or a RuneC tool with tests.
5. Add the output to schemas/manifests/reports.
6. Delete the importer path that read the outside repo.
7. Add validation that prevents the outside repo path from being used again.

Do not solve gaps by keeping an external repo checkout as an input.

## Required Guard Tools

Add `tools/validate_no_external_repos.py`.

It should fail if any of these are true:

- A nested `.git` directory exists under the RuneC root, except the top-level
  `.git`.
- `.gitmodules` exists.
- Active code or scripts contain hard dependencies on:
  - `data/source/runelite`
  - `data/source/osrsreboxed-db`
  - `data/source/data_osrs`
  - `data/source/void_rsps`
  - `data/source/near_reality`
  - `data/source/2011Scape-game`
  - `tools/cache_pipeline/source/rsmod`
  - `RUNEC_RSMOD_ROOT`
  - `RuneC-DB`
  - `git clone https://github.com/runelite`
  - `git clone https://github.com/rsmod`
  - `raw.githubusercontent.com` for generated data inputs
- Exporters import `RUNELITE`, `OSRSREBOXED`, `DATA_OSRS`, or a similar
  external repo path from `tools/source_paths.py`.
- Runtime manifests or generated reports record blocked/private-server
  provenance.

It may allow policy docs such as this file, `data_cleanup.md`, and
`git_setup.md` to name blocked sources when explaining why they are banned.

Add `tools/validate_pipeline_inputs.py`.

It should fail if a pipeline stage reads from any path that is not declared in
its stage manifest. Stage manifests should separate:

- tracked RuneC source inputs;
- explicit external raw cache input paths passed by maintainers;
- ignored generated outputs;
- release artifacts.

## Pipeline Stages

The target command remains:

```bash
python3 tools/data_pipeline.py all
```

Normal data builds should use that top-level command. Individual exporters under
`tools/` and `tools/cache_pipeline/` are lower-level maintainer/debug tools
until they are wired into a declared pipeline stage with explicit inputs,
outputs, and validation.

Phase 4 also adds:

```bash
python3 tools/data_pipeline.py --check
python3 tools/data_pipeline.py --clean-generated all
python3 tools/data_pipeline.py list-stages
```

`--check` validates the current local generated outputs without rebuilding
runtime packs. `--clean-generated` removes only pipeline-owned generated
manifests, packs, reports, and records before running the selected command.

The stages should be:

```text
validate-repo-self-contained
validate-source-authority
validate-content
export-content
export-cache-derived-assets
export-defs
export-render-assets
pack-runtime-data
unpack-runtime-data
generate-reports
validate-reports
```

### `validate-repo-self-contained`

Runs:

- `tools/validate_no_external_repos.py`
- nested repo/submodule checks
- active-code dependency scans
- stale docs scan for setup instructions that require external repos

This stage must pass before any data release is publishable.

### `validate-source-authority`

Confirms generated outputs do not contain blocked-source provenance.

Blocked:

- VoidPS
- 2011Scape
- Near-Reality
- Zenyte
- arbitrary RSPS/private-server sources
- cloned RuneLite, RSMod, osrsreboxed, or data_osrs directories as active
  exporter inputs

Allowed steady-state authorities:

- RuneC-owned code and tools.
- RuneC-owned curated content under `content/`.
- b237 cache input passed explicitly by maintainers for rebuilds.
- RuneC release manifests and packs for users.

### `validate-content`

Checks tracked source-of-truth content:

- `content/catalog.toml`
- `content/world/*`
- `content/items/*`
- `content/npcs/*`
- `content/combat_visuals/*`
- `content/spells/*`
- `content/quests/*`
- `content/dialogue/*`

Each table should declare owner, schema, provenance note, and whether it is
cache-derived, curated, or gap-filler.

### `export-cache-derived-assets`

Uses RuneC-native cache decoders to produce terrain, object placements, models,
sprites, animations, spotanims, UI data, and symbol tables.

This stage must not depend on Joshua-F `osrs-dumps` as a checked-out repo. If
the existing dump has data the pipeline still needs, first build the equivalent
RuneC extractor or convert the required subset into a checked, reviewed
RuneC-owned table.

### `export-defs`

Builds gameplay/runtime definitions from:

- b237 cache-derived exports;
- tracked RuneC content tables;
- tracked RuneC schemas;
- RuneC-owned source-gap tables.

It must not read osrsreboxed, data_osrs, RuneLite, RSMod, VoidPS, 2011Scape, or
Near-Reality directories.

### `pack-runtime-data`

Packs only RuneC-generated runtime files.

The manifest should record:

- RuneC commit;
- data pipeline version;
- data version;
- source lockfile hash;
- source authority policy hash;
- schema versions;
- content catalog hash;
- b237 cache identifier if used by a maintainer rebuild;
- pack checksums;
- loose asset checksums for required runtime paths;
- required logical runtime paths;
- optional logical runtime paths;
- self-contained validation result;
- blocked-source validation result.

It writes both `dist-data/manifest.json` for release packaging and
`data/manifest.json` for the local loose-file install.

`tools/pack_runtime_data.py --force` owns `dist-data/packs/*.pak` and removes
stale generated packs that are not listed in the current manifest.

### `unpack-runtime-data`

Verifies that the generated runtime packs can hydrate the local `data/` tree
through `tools/unpack_runtime_data.py`.

The stage should not use any external RuneScape repo checkout. It reads only
`dist-data/manifest.json`, `dist-data/packs/`, and the local `data/` install
path. It writes `data/.runtime-unpacked` as the local install marker.

Runtime startup validates `data/manifest.json` through
`rc_game_data_validate_install()` before loading a world. Required logical paths
must exist in either the loose install or manifest-listed packs, and blocked
runtime provenance is rejected unless a developer explicitly sets
`RUNEC_ALLOW_BLOCKED_SOURCE_PROVENANCE=1`.

### `generate-reports`

Collects generated validation and completion reports under
`generated/reports/` so release validation can inspect one report tree instead
of mixing source docs, old report locations, and runtime data.

### `validate-reports`

Runs `tools/validate_reports.py` against `generated/reports/`, `data/`, and
`dist-data/`.

The report gate checks required reports, allowed statuses, activity
`BLOCKS_PARITY` counts, blocked runtime provenance, explicit source-gap rows,
aggregate/subreport count consistency, and accepted limitations. It writes:

```text
generated/reports/report-validation.json
generated/reports/data-v1-summary.json
generated/reports/data-v1-summary.txt
```

The current expected release status is `not_publishable_source_gaps` until the
remaining source-authority gaps are resolved. `tools/validate_runtime_data_lock.py`
keeps `runtime-data.lock` in draft/non-official mode, with empty release URLs
and checksums, while that status remains.

- Exporters for official data should read reviewed RuneC content tables, not

### Remove Private-Server Inputs

Targets:

- Delete `data/source/void_rsps`.
- Delete `data/source/near_reality`.

### Resolve Raylib Vendor Policy

`lib/raylib` is not an RS repo, but it is an embedded third-party code/binary
dependency. It should be made explicit.

Choose one policy:

- Use system/package `raylib` and remove `lib/raylib`.
- Or create a clear `third_party/` policy with license, version, checksums, and
  update procedure.

Do not keep it as an unexplained hidden codebase.

## Phase Placement

If Phase 0 and Phase 1 are already done, the next phase should be:

### Phase 1C: Remove External Repo Dependencies

This must happen before source locking and before an official new data release.

1. Add `tools/validate_no_external_repos.py`.
2. Add `tools/validate_pipeline_inputs.py`.
3. Remove active exporter imports of `RUNELITE`, `OSRSREBOXED`, and
   `DATA_OSRS`.
4. Remove the RSMod hard requirement from `tools/export_combat_visuals.py`.
5. Move needed facts into RuneC-owned `content/` tables.
6. Move raw b237 cache input outside the repo root or make every cache path an
   explicit maintainer argument.
7. Delete blocked local mirrors:
   - `data/source/void_rsps`
   - `data/source/near_reality`
8. Remove stale `RuneC-DB` clone instructions from docs.
9. Make official data generation fail if any external repo path is read.

### Phase 2: Source and Content Locking

After Phase 1C, source locking should lock RuneC-owned sources, not external
repo checkouts.

Track:

- `content/catalog.toml`
- `content/**` source hashes
- schema versions
- b237 cache identifier used for maintainer rebuilds
- tool versions
- gap report hashes

Do not track:

- RuneLite checkout revisions
- RSMod checkout revisions
- osrsreboxed checkout revisions
- data_osrs checkout revisions
- private-server repo revisions

Those should not be pipeline dependencies.

## Success Criteria

The data pipeline is self-contained when:

- A clean clone can build RuneC code without any external RS repo checkout.
- A clean clone can run after `./scripts/setup-data.sh` downloads RuneC-owned
  runtime packs from an official `runtime-data.lock` release, or after a
  maintainer installs locally generated packs with
  `./scripts/setup-data.sh --offline dist-data` while the lock remains draft.
- No nested `.git` directories or submodules exist under the RuneC root.
- No active exporter reads `data/source/*` repo mirrors.
- No active exporter reads `tools/cache_pipeline/source/rsmod` or
  `data/source/runelite`.
- `tools/source_paths.py` no longer exposes external repo roots.
- `tools/export_combat_visuals.py` does not require RSMod.
- `tools/export_item_effects.py` does not require RuneLite.
- Item/NPC stats do not require osrsreboxed.
- Spawns/transports/traversal do not require data_osrs.
- Full external dumps are not required under the repo root.
- Any missing fact becomes a source-gap row instead of a hidden external
  dependency.
